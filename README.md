# ApplyShield
**Don't Apply Blindly. Verify First.**

ApplyShield is a recruitment-risk signal checker. It highlights common warning patterns in job and internship messages, shows matching evidence, and suggests independent verification steps.

## Current project status

- Frontend: working HTML/CSS/Vanilla JavaScript demo.
- Local analysis: deterministic rule-based demo mode; no external AI service.
- AWS backend: SAM scaffold with API Gateway, Lambda, Step Functions, DynamoDB and S3 resources.
- AWS deployment: not performed by this repository. You must configure an AWS account, deploy the SAM template, and connect the frontend API URL.

## Run the frontend locally

The frontend uses browser JavaScript modules and localStorage. Serve the `frontend` directory with a local static server; do not open the HTML file directly.

For example, with Python installed:

```bash
cd frontend
python -m http.server 5500
```

Open `http://localhost:5500`.

Try this sample message:

> Congratulations! You have been selected for our remote internship. Pay ₹999 as a registration fee to confirm your position. Guaranteed selection. Contact our recruiter on WhatsApp.

The local demo performs simple text-pattern checks. It does not verify companies, domains, job listings, or actual fraud.

## AWS backend deployment

Prerequisites:
- AWS account and configured AWS credentials
- AWS SAM CLI
- Node.js 22+
- An AWS region with the listed services available

From `backend/`:

```bash
sam validate
sam build
sam deploy --guided
```

After deployment, copy the `ApiBaseUrl` output into `frontend/js/api.js` as `API_BASE`. Then rebuild/redeploy the static frontend.

### Important integration work before using the AWS API

The starter backend is a challenge scaffold, not a production-ready public service. Before connecting the frontend:
1. The frontend now creates and sends a browser-generated `x-session-id` capability token. This is suitable only for a controlled demo; it is not full authentication. Add a proper identity provider/authentication layer before public production use.
2. Add authentication/authorization and rate limiting. Do not expose the API publicly without abuse controls.
3. Confirm CORS origins are restricted to your deployed frontend domain.
4. Test SAM template and Step Functions definition in your AWS account.
5. Add failed-workflow status persistence and operational logging/alarms.
6. Implement secure evidence deletion and a retention policy appropriate to your use case.

## AWS architecture

Browser → API Gateway → Lambda → Step Functions → extraction → risk detection → verification-gap analysis → scoring → DynamoDB report persistence.

Evidence uploads use short-lived S3 presigned URLs generated by Lambda. S3 blocks public access and applies encryption and lifecycle expiration.

## Project limitations

- The current scoring engine is a transparent heuristic, not a machine-learning classifier.
- A risk score is not a probability of fraud.
- A lack of detected warning signals does not establish legitimacy.
- The initial backend analyzes pasted text. File upload to S3 is scaffolded, but server-side image/PDF OCR is not implemented; an uploaded image/PDF is stored as evidence and is not interpreted by the current analysis workflow.
- The current AWS starter should be tested and security-hardened before public deployment.

## Deployment hardening update

- Workflow failures now invoke a dedicated `FailureHandlerFunction` that records `FAILED`, `failedAt`, and a generic user-safe `failureMessage` in DynamoDB.
- If `StartExecution` itself fails after the initial DynamoDB write, the start-analysis Lambda now marks that record `FAILED` and returns HTTP 503.
- This is still an MVP: the browser-generated session ID is a capability token, not authentication; API and S3 CORS are currently permissive; uploaded images/PDFs are stored but not OCR-processed; no external company identity verification is performed. Restrict CORS and add real authentication before production use.


## Public-demo security configuration (no sign-in)

This challenge MVP intentionally does not use Cognito or another user-login system. Its API routes remain publicly callable. The template applies API Gateway stage throttling (5 requests/second, burst 10) and requires an exact `FrontendOrigin` parameter for API and S3 CORS. CORS is a browser control, not authentication; non-browser clients can still call public endpoints. The browser-generated `x-session-id` is a demo namespace/capability token and must not be treated as identity or authorization. Do not store sensitive personal data or confidential recruitment documents in this demo.

When running locally, use a local web server whose origin exactly matches `http://localhost:5500`, or pass the actual frontend origin at deployment. When the frontend is hosted, redeploy with `FrontendOrigin` set to that exact origin (scheme + hostname + optional port, no path and no trailing slash). Keep the S3 bucket private; uploads use short-lived presigned URLs. Review API Gateway throttling and AWS service costs before public release.
